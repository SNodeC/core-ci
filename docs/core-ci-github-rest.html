Scope & evidence

One daemon boundary, explicit callers

Solid arrows are requests or local calls; dashed arrows are replies. Internal calls and database commits are shown to explain when a REST acknowledgment becomes durable. Alternative and loop frames are rendered by Mermaid itself. A sequence is a representative ordering unless a parallel frame or a dedicated race diagram says otherwise; independent requests have no implied global order.

The authoritative runtime state is the committed MariaDB event history replayed into one engine. Tags and declarations describe desired work; only accepted committed events change execution state. Dashboard GitHub observations and presentation bookkeeping do not become a second execution authority. This review changes no architecture or production behavior.

“GitHub → core-ci” distinguishes GitHub’s webhook service, an Actions runner executing the reporting action, and a runner fetching public status. A README badge fetch may come from GitHub’s image proxy or a browser. Admin and dashboard clients are listed separately; no current workflow is claimed to call an admin endpoint.

Shared wire contracts

Authentication, payloads and response meanings

Webhook: JSON with X-GitHub-Event, X-GitHub-Delivery, and X-Hub-Signature-256: sha256=<HMAC(secret, rawBody)>. Uses CORECI_WEBHOOK_SECRET.

Callback: URL-encoded form with X-CoreCI-Timestamp and X-CoreCI-Signature-256: sha256=<HMAC(secret, timestamp + "." + rawBody)>. Uses CORECI_CALLBACK_SECRET, clock skew ≤ 300 seconds. The encoded path buildId is decoded exactly once. Missing/invalid fields, malformed escapes and duplicate form keys are rejected; unused valid fields are ignored.

Daemon outbound: TLS with chain and hostname verification; Bearer CORECI_GITHUB_TOKEN, GitHub API version 2022-11-28, raw or JSON Accept, one request per connection, 30-second exchange deadline, no transport reconnect/retry or redirects. No bearer credential or HMAC secret is placed into workflow inputs.

Dispatch input schema: build = build_id, package, version, revision, target, callback_url, source_repo, tag, prerequisites; publish = build_id, package, version, revision, target, callback_url, build_repo, build_run_id, artifact; presentation = feed, generation. Every input value is a string. Build/publish JSON ref is the workflow repository’s default branch; presentation JSON ref is the registry repository’s default branch.

Callback variants: build started requires run_id, run_attempt; build succeeded requires run_id, artifact; build failed requires run_id, reason; publish succeeded requires run_id, feed_commit; publish failed requires run_id, reason; publish started emits no event and does not require run fields. Every event also uses the path buildId and server-stamped event time.

A 200 accepted event response means the event committed and was applied, not that all workflows it may schedule succeeded. A 204 from GitHub means dispatch accepted, not workflow completed. A 202 reload response acknowledges scheduling, not valid declarations. A lost or failed external response never proves the external mutation did not happen.

Observed architecture and differences

Behavior that must stay visible in the diagrams

F1 — Failed units miss dashboard job lookups on reviewed main. The typed snapshot carries Failed(reason), but Model.cpp compares it with exactly Failed in selection and request eligibility. As a result, failed units are not requested through the job cache. The serialized public JSON does split kind/detail, but the lookup code reads the typed snapshot before that split. PR #67 at 3569707 changes these checks to prefix matching and preserves the failure’s build/run identity. That pending behavior is not attributed to main. Sources: core/Status.cpp, app/StatusJson.cpp, adapters/dashboard/Model.cpp.
F2 — Publisher discovery can precede accepted dispatch on reviewed main. Current request selection includes publishers in PublishDispatching, including rejected dispatch/backoff, and for settled units. The pending PR #67 gates publisher lookups on existing publishDispatchedAt, set only by an accepted committed publication dispatch. Both versions discover publisher run IDs by listing runs; neither stores them as the builder run ID. Sources: adapters/dashboard/Model.cpp, core/Engine.cpp.
  • Repeated repository scans are implemented behavior. Unknown-run lookups scan every repository run page separately for each cache key. No quota or latency conclusion is established by source review alone. The four-slot bound applies only to job lookups, not all GitHub traffic. D21–D23.
  • Callbacks drive execution; job polling does not. A completed or failed job-cache observation cannot synthesize a build/publish result. Missing callbacks eventually use engine deadlines. D11–D17, D23.
  • Dispatch execution can repeat. Timeout, lost response, or Resumed may resend the same workflow_dispatch. Callback/engine idempotence does not guarantee one GitHub run. D18–D19.
  • Presentation has no completion feedback. A 204 can clean a snapshot even when the later writer fails. A subsequent status change or process startup can re-dirty it; job polling does not track the presentation writer. D20.
  • Build and publisher run IDs differ. Published/failure run fields retain the builder identity; publisher callbacks’ run IDs are not an expected-run authentication gate. D16–D17, D22.
  • No daemon-side App lifecycle or artifact API. There is no installation-token minting, token refresh, GraphQL, GitHub check/status mutation, run cancellation/re-run, artifact transfer or feed Git push in this daemon. Standard actions and Python/Git tooling may do those things on runners; those requests do not cross the daemon boundary. D01, D10, D26.

D01 · Outbound

Common outbound transport and authentication

Every daemon-to-GitHub request uses this transport. The configured API origin defaults to https://api.github.com; its optional path prefix is retained. TokenProvider reads CORECI_GITHUB_TOKEN for each request. No GitHub App token-minting or refresh endpoint is implemented in core-ci. GET is selected when the optional request body is absent, POST when present. Non-raw requests accept application/vnd.github+json; declaration contents accept application/vnd.github.raw. All requests send X-GitHub-Api-Version: 2022-11-28, Authorization: Bearer <environment token>, User-Agent: core-ci and Connection: close. POST adds Content-Type: application/json. Each exchange has its own 30-second deadline, including connection setup; transport retry and reconnect are disabled. TLS chain and hostname checks complete before any HTTP request bytes are sent. Redirects are not followed. Error handling belongs to the caller, as shown in the following diagrams.

D02 · Inbound

Common inbound validation and durable event acknowledgment

Applies to event-carrying webhook, callback, retry and rebuild requests. Parser limits are at most 25 MiB body, 64 KiB headers, 100 header fields and 8 KiB start line; configured smaller limits also apply. A middleware rejects bodies over 64 KiB except on the webhook path before authentication. Routes are case-sensitive and strict. Path parameters are percent-decoded once by the framework; malformed path escapes can return 400 before middleware. HMAC authentication precedes content parsing. Accepted events are normalized and classified, then appended and committed before engine mutation and before a 200 accepted response. Commands are scheduled on a zero-delay timer after commit, so the outbound request need not precede the inbound response. Ignored events are neither stored nor applied. The smoke assertions expect 431 for header/start-line limits and 413 for body limits. A failed append has unknown commit outcome: return 503, discard state and replay. These alternatives apply to every callback diagram below, even where only the accepted path is drawn.

D03 · Inbound

Webhook ping, ignored events and delivery deduplication

POST /api/v1/github/webhook requires X-Hub-Signature-256 = sha256=<lowercase HMAC-SHA256 of the exact raw body using CORECI_WEBHOOK_SECRET>. Signature comparison is constant-time. X-GitHub-Event, X-GitHub-Delivery and application/json are required after authentication; even ping and unsupported events must contain a JSON object. Ping is answered before deduplication. Malformed JSON or non-object JSON returns 400, including for unsupported events. The deduplication deque retains the last 1000 remembered IDs in memory and is empty after restart. Only scheduled default-branch reload deliveries and successfully processed known-repository tag deliveries are remembered. Unsupported events, ignored branches/tags and unknown repositories are not remembered. GitHub create/delete/release events are ignored; tag handling uses push. No release, workflow_run, workflow_job, check_run, pull_request, repository_dispatch or installation event is handled as an engine event.

D04 · Both

New tag webhook to dependency-aware build scheduling

The actionable tag payload has ref=refs/tags/<tag>, created=true, deleted=false, repository.full_name and after. A moved existing tag or deleted tag is ignored. Repository matching is case-insensitive. An unknown source repository returns 202 ignored; a tag arriving while the engine is unavailable returns 503. For known packages, TagObserved carries origin=Webhook and sourceSha=after. The SHA must normalize to 40 lowercase hexadecimal characters; it is informational, and workflows check out the tag. Only a newer accepted SemVer release changes state; invalid version syntax, equal/older versions and disabled prereleases produce 200 ignored. Per-package response lines are aggregated with the highest status; the delivery is remembered only if every result is 200. The graph currently validates one declaring package per repository, although the handler supports a batch. A valid new release may immediately dispatch independent ready targets or wait for their prerequisites and the configured build-slot limit.

D05 · Both

Default-branch webhook and all declaration-reload triggers

A non-deleted refs/heads/<branch> push triggers a reload only when branch equals repository.default_branch in the payload and the repository is the configured registry or a source repository in the current graph. A workflow-only repository is not separately watched unless it is also the registry/source repository. Other branches/repositories return 202 ignored. Reload is asynchronous: 202 reload scheduled acknowledges scheduling, not successful declaration loading or graph replacement. Further reload triggers during a load set one reloadPending boolean; one additional load starts when that load ends. Other reload triggers are listener startup, successful store recovery, the reconcile-interval timer (default 900 seconds), admin POST /api/v1/reload and dashboard POST /api/refresh. Every load attempt, successful or failed, calls reconcile(true) against the available current graph. A follow-up load can overlap an already running tag reconciliation; independent repository requests are not globally serialized.

D06 · Outbound

GET repository metadata and resolve workflow references

GET /repos/{owner}/{repo} resolves full_name and default_branch. The loader begins with the registry repository, then resolves the union of source repositories, build workflow repository, publisher repositories and presentation workflow repositories. It deduplicates these identities case-insensitively within a load. A successful metadata read is followed by the default-branch commit read in D07, including for workflow-only repositories. Distinct unresolved repositories are fetched independently. The canonical owner/name is used for subsequent requests, stored graph identities and dispatch paths. Invalid repository/default-branch data, malformed JSON or any non-200 response fails the whole declaration load. There is no persistent metadata cache across loads, and core-ci does not fetch workflow YAML to validate its contents.

D07 · Outbound

GET default-branch HEAD and raw declaration contents

GET /repos/{owner}/{repo}/commits/{branch} must return 200 and a 40-character lowercase hexadecimal sha. The loader reads every contents file at that resolved SHA, not at a moving branch name: GET /repos/{owner}/{repo}/contents/{encodedPath}?ref={sha}, with Accept: application/vnd.github.raw. The whole relative path is percent-encoded, including slashes (ci/packages.json becomes ci%2Fpackages.json). The registry file and target catalog share the registry SHA; each source declaration uses that source repository's independently resolved SHA. This is per-repository consistency, not a globally atomic snapshot across repositories. Load order is registry resolution and contents, catalog contents, referenced repository resolution, then source package contents in parallel. A raw file over 1 MiB, duplicate JSON key, schema/type/identifier/catalog/graph validation failure or HTTP error fails the whole load. After a load fails, outstanding requests may finish but cannot deliver a second result or apply a partial graph. One successful result enqueues GraphChanged. An unchanged graph is ignored; a graph change unsafe during publication is also ignored and retried by a later reload. Presentation/catalog/details are installed only if the engine's resulting pipeline equals the loaded pipeline. A load error is shown as the first line of text status; the old graph stays active.

D08 · Outbound

GET source tags with complete pagination and reconciliation

For every source repository in the active graph, GET /repos/{owner}/{repo}/tags?per_page=100. Follow Link rel=next only after validating the complete Link header: HTTPS, same host and port as the configured API origin, no malformed syntax, no duplicate next relation and no repeated visited path. Pages for one repository are sequential; different repositories proceed independently. Only after all pages succeed does each package select the highest accepted SemVer; disabled prereleases are excluded and ties choose the lexicographically smallest tag string. Every tag entry must have a 40-character lowercase hexadecimal commit SHA. Any bad page, SHA, Link, repeated path, non-200 response, transport failure or redirect aborts only that repository with no TagObserved from its partial results. A later round retries it from page one; there is no immediate HTTP retry. Reconciliation runs after every load attempt and on admin POST /api/v1/reconcile. The admin operation declines another ordinary round while reconciling, but a post-load round is allowed to overlap. A new observed release uses the same engine scheduling as a webhook.

D09 · Outbound

POST build workflow dispatch

POST /repos/{workflowOwner}/{workflowRepo}/actions/workflows/{workflowFile}/dispatches uses the configured build workflow repository, not necessarily the package source repository. JSON ref is that workflow repository's resolved default branch. inputs contains exactly build_id, package, version, revision, target, callback_url, source_repo, tag and prerequisites. Every input value is a string. prerequisites is a sorted comma-separated list such as a=1.2.3-4,b=2.0.0-1, or the empty string. callback_url is the configured callback base with trailing slashes removed plus /api/v1/builds/{percentEncodedBuildId}/report. Build IDs are package~target~version~rN; version build-metadata plus signs become %2B in the URL. The dispatch body does not include attempt, source SHA, feed, recipe_ref, token or HMAC secret. Before sending, app reclassifies a prospective DispatchAccepted against current engine state and skips stale commands/recovery. Only HTTP 204 records DispatchAccepted; every other status, including 200/201/202/3xx, records DispatchRejected. The response contains no run ID used by core-ci. A started callback or terminal build callback establishes run identity.

D11 · Both

Dispatch rejection, backoff, deadlines and automatic retry

Applies to both build and publication dispatches. DispatchAccepted/Rejected is applicable only to the matching current buildId, phase, dispatch attempt and no retryAt; stale results are ignored. A non-204 status becomes DispatchRejected(httpStatus, body); transport error is status 0. HTTP 401/403/404/422 fails immediately and never schedules automatic retry. Other statuses, including 429, 3xx and 5xx, use engine backoff min(30 seconds * 2^(attempt-1), 1800 seconds), measured from committed rejection engine time. With the default maximum of 8 dispatch attempts, delays before attempts 2 through 8 are 30, 60, 120, 240, 480, 960 and 1800 seconds. Tick checks run every 30 seconds, so sends occur on the first due timer pass. Retry uses the same buildId and payload, increments the internal dispatch attempt, and does not re-check readiness. No Retry-After header or remaining-rate-limit header is used. 204 begins a build timeout of 21600 seconds or publish timeout of 3600 seconds by default. A callback can also establish that phase/deadline before 204. Terminal execution failure, timeout or exhausted transient dispatch retries can schedule one automatic retry per version and prerequisite-input tuple after retryDelay (default 600 seconds, 0 disables). That retry clears failure and rebuilds with a new revision/buildId through the ordinary scheduling rules; it is distinct from resending a dispatch.

D19 · Both

Startup, unknown commit outcome and dispatch resumption

At startup the event store obtains its single-writer lock, loads committed history and replays it with all replay-produced commands discarded. One Resumed event is then committed. It re-emits unchanged buildId/attempt commands only for Dispatching or PublishDispatching with no retryAt. Existing backoffs, running phases and their deadlines remain as replayed; a late startup Tick handles due deadlines. The listener is first started after Resumed. Runtime store loss discards the engine, answers affected/new event requests 503 and rebuilds; open/load transient failures use 1-second exponential backoff capped at 60 seconds, while corrupt schema/history is fatal. A dispatch result received while queue.engine() is unavailable is logged and dropped; after recovery Resumed may resend it. If an event actually committed despite an append error, replay sees it and a sender retry is ignored. If no event committed, sender retry can apply it. This is deliberate uncertainty handling, not an assumption that the previous mutation failed. In-memory webhook IDs, presentation dirty tracking and job cache are not durable and refill/reset after process restart.

D25 · Both

Administrative and dashboard operations that trigger GitHub calls

Admin endpoints are POST /api/v1/units/{package}/{target}/retry, /rebuild, /api/v1/reload and /api/v1/reconcile, requiring constant-time matching Authorization: Bearer <CORECI_ADMIN_TOKEN>. Retry applies only to an active failed unit with no in-flight build; rebuild applies only to a satisfied active unit with no in-flight build. An applicable event is committed before 200 accepted and ordinary scheduling; an inapplicable event returns 200 ignored, and store unavailability returns 503. Retry rebuilds using a new revision rather than re-running a GitHub job. Reload and reconcile return 202 started or already running immediately, including when no new work actually starts because the engine is unavailable. A reload trigger during a load also schedules one pending follow-up. Dashboard POST /api/retry with JSON {package,target} uses the same RetryRequested event, but OIDC/session+subject allowlist auth, not the admin token. POST /api/refresh requires application/json and waits for the declaration-load callback, returning JSON 200 Declarations loaded or 503 Declaration load failed; coalesced reload replies wait until pending reloads drain. Other /api/{operation} names return JSON 400 Not supported by core-ci, rather than proxying to the admin endpoints. These endpoints have no built-in GitHub caller; an authorized workflow could call an admin route as any HTTP client could. Their inclusion covers all local triggers for the outbound interactions, not a claim that existing workflows invoke them.

Complete successful lifecycle and independent downstream work

This overview composes the detailed diagrams. A source release is observed by either a signed tag webhook or tag reconciliation. The committed graph and release/input state alone decide ready work. The build workflow reports started then a terminal result; the publisher reports only a terminal result. A build success can dispatch publishing before GitHub marks the build run completed, because the final report job is still finishing: GitHub-side publisher provenance checking polls that build run for up to 300 seconds before requiring successful completed provenance. This poll is runner-to-GitHub REST, not an additional daemon API. Each target's prerequisite publications govern its dependents; separate ready builds and separate feeds may proceed concurrently. Dashboard GitHub job reads observe progress but never drive engine transitions. A presentation writer can later refresh the public feed view, and publication itself can fetch/render status. Git checkouts/pushes, package downloads, GHCR/image pulls, Actions artifact transfer and App-token creation by standard workflow actions are runner/provider operations; they do not cross the core-ci daemon boundary and are not mislabeled as core-ci REST calls.
